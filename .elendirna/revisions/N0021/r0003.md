## Delta

## 보완 제안: md/link 기반 현재 구조에서의 첨부파일 기능 현실화 (2026-04-24)

현재 코드 기준으로 첨부파일의 토대는 이미 부분적으로 존재한다.

- `manifest.toml`에는 `sources: Vec<String>` 필드가 있다.
- validator는 `assets/` 디렉터리와 `sources`의 dangling/미등록 상태를 점검한다.

즉, "첨부파일을 전혀 모르는 상태"가 아니라 "파일 메타데이터와 무결성 정보가 부족한 상태"다.

### 판단

이미지 같은 첨부파일 저장은 충분히 타당하며, 다음 이유로 권장한다.

1. md 기반 워크플로와 잘 맞음
- note/revision에서 `![...](../../.elendirna/assets/...)` 또는 별칭 링크를 사용하면 텍스트+증거를 함께 보관 가능.

2. 실무 증거 보존에 유리
- 로그 스냅샷, 다이어그램, UI 캡처, PDF를 함께 남기면 후속 AI 세션의 환각을 줄인다.

3. 현재 구조를 크게 깨지 않고 확장 가능
- `sources`와 `assets`를 첨부파일 레이어로 승격하면 된다.

### 권장 구현 단계

#### 1단계(MVP): 관리 명령 + 기본 무결성
- `elf entry attach <ID> <FILE_PATH>`
  - 파일을 `assets/`로 복사
  - `manifest.sources`에 파일 키 등록
- `elf entry detach <ID> <FILE_KEY>`
  - `manifest.sources`에서 제거
  - 다른 entry에서 참조 없으면 삭제
- `elf validate --full`에서만 해시 검증
  - 기본 validate는 존재/크기 점검

#### 2단계: `sources`를 구조화
`Vec<String>` 대신 구조체 배열(예: `[[sources]]`)로 확장:
- `key` (저장 파일명)
- `orig_name`
- `mime`
- `size`
- `sha256`
- `added_at`
- optional: `caption`, `kind`(image/log/pdf)

#### 3단계: 중복 제거(CAS)
- 저장 키를 `sha256.ext`로 두고 content-addressable 저장
- 동일 파일은 복사 없이 reference만 추가

### 경계 조건

- 대용량 바이너리는 git 저장소를 빠르게 비대화시킨다.
- 정책 필요: 예) 기본 20MB 경고, 50MB hard-limit(옵션으로 override)
- 장기적으로는 원격 object storage 연동도 후보.

### 결론

"이미 md 기반이고 링크가 가능하니 굳이 첨부를 시스템화할 필요가 있나"에 대한 답은,
운영 초기에 수동 링크로 시작할 수 있지만 실무 신뢰도를 확보하려면 결국 attach/detach/validate가 필요하다는 쪽이다.

현재 코드의 `assets + sources`는 이 방향의 좋은 출발점이며,
N0021은 신규 기능 제안이라기보다 기존 토대를 제품 수준으로 끌어올리는 정리로 보는 것이 맞다.
