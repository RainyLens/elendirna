## Delta

## 보완 제안: 홈랩 기반 Web MCP 호스팅 검토
중요도는 낮음~중하. 당장 구현 항목은 아니며, 향후 HTTP/SSE 기반 Web MCP 서버를 만들 때 고려할 운영 시나리오로 기록한다.

## 사유
개인 지식 관리 vault를 집의 홈랩 서버에서 호스트하고, 외부 AI 클라이언트나 여러 작업 환경에서 API key 형식으로 접근하고 싶은 요구가 있다.

현재 stdio MCP는 로컬 프로세스 기반이라 단일 장비/단일 세션에는 단순하고 안전하지만, 다음 요구에는 부족하다.

- 집/업무용 노트북/다른 환경에서 동일 private vault 확인
- 여러 AI 클라이언트가 같은 vault context를 복원
- 로컬 파일 경로를 직접 공유하지 않고 HTTP endpoint로 제공
- API key 단위로 접근 권한을 관리

## 추가 검토 사항

### 1. Vault 노출 경계
Web MCP는 원격 접근이 가능하므로 vault 선택 실수의 비용이 커진다.

- 서버 기동 시 명시적인 `--vault <path>` 또는 config 기반 root 고정 필요.
- cwd 기반 intent signal은 사용할 수 없음.
- public-compatible vault와 private workbench vault를 명확히 분리해야 함.
- 기본값으로 global/local fallback을 허용하면 안 됨.

### 2. API key 권한 모델
단순한 단일 shared key로 시작할 수 있지만, 장기적으로는 key별 scope가 필요할 수 있다.

후보 scope:

- read-only: `entry_list`, `query`, `entry_show`, `bundle`, `validate`
- write: `entry_new`, `revision_add`, `sync_record`, `entry_status`
- admin: key 발급/폐기, vault 설정 변경

초기 MVP는 read/write 2단계만으로 충분할 수 있다.

### 3. 쓰기 작업 안전장치
원격 Web MCP에서는 실수 기록이나 wrong-vault write가 더 위험하다.

- write key 사용 시 `sync_record`/`revision_add`의 author 식별 필요.
- N0046의 1-step undo 필요성이 더 커진다.
- 실무/개인 맥락이 들어가는 것을 막기 위한 warning/quarantine 가능성 검토.

### 4. Transport / Deployment
후보 구성:

- 홈랩 내부 reverse proxy 뒤에서 HTTPS 제공.
- MCP HTTP/SSE endpoint는 localhost 또는 VPN/Tailscale 내부망 우선.
- public internet 직접 노출은 지양.
- API key는 header 기반 bearer token 또는 `X-Elf-Key` 형태 검토.

### 5. Audit / Observability
원격 서버는 누가 어떤 vault를 읽고 썼는지 추적이 필요하다.

- key id, agent, operation, entry id, timestamp 기록.
- raw request body 전체 저장은 지양.
- 실패한 auth 시도 rate limit 고려.

## 초기 판단
이 요구는 `N0033`의 HTTP MCP 설계와 직접 연결된다. 다만 현재는 단일 사용자 dogfooding 수준에서는 stdio MCP와 private workbench git sync가 더 단순하다.

따라서 Web MCP 홈랩 호스팅은 구현 우선순위를 낮게 두되, 실제 필요가 반복되면 다음 순서로 검토한다.

1. read-only Web MCP
2. API key 기반 read/write scope
3. author/audit 기록
4. 1-step undo 또는 write quarantine과 결합

## 결론
Web MCP는 단순 transport 변경이 아니라 vault visibility, auth, audit, write safety 문제를 함께 여는 기능이다. 홈랩 서버에서 private vault를 API key로 제공하는 시나리오는 유효하지만, public/private 경계와 write safety가 충분히 정리된 뒤 추진하는 것이 적절하다.
