## Delta

## 중복 기록 탐지의 한계와 저비용 후보 (2026-04-24)

사용자 관찰:
기록 전에 이미 비슷한 내용이 있는지 확인하고, 중복이면 새 기록 대신 기존 entry/revision을 참조하거나 보충하는 흐름이 있으면 좋다. 다만 MCP 자체에 저부하 LLM이 붙어 있지 않은 이상 의미적 중복 판단은 어렵다.

해석:
- 정확한 중복/유사 의미 판단은 LLM 또는 embedding 계층이 가장 잘한다.
- 그러나 매 기록마다 고성능 LLM을 호출하는 것은 비용/지연/복잡도 면에서 부담이 크다.
- Elendirna 코어는 LLM 내장보다, entry/revision/source-of-truth 구조를 유지하고 외부 AI가 필요 시 판단하는 쪽이 더 단순하다.

가능한 저비용 대안:
1. 제목/태그/본문 키워드 기반 후보 검색
   - `query(title_contains=...)`, tag 검색, 단순 substring/FTS
   - 장점: 구현 단순, deterministic
   - 단점: 의미 중복은 놓침

2. sqlite FTS 인덱스
   - note/revision 텍스트를 FTS5로 인덱싱해 유사 후보를 빠르게 반환
   - 장점: LLM 없이 중복 후보 제시 가능
   - 단점: 최종 판단은 여전히 사람/AI 몫

3. cheap fingerprint
   - normalized title, 주요 키워드, entry id refs 등을 기반으로 근사 중복 후보 생성
   - 장점: 저비용
   - 단점: 품질 제한

4. 외부 AI에게 맡기는 prompt-level workflow
   - 기록 전 `query`/`bundle`로 후보를 보고, AI가 중복 여부를 판단
   - 장점: 현재 구조와 잘 맞음
   - 단점: 모델 비용/컨텍스트 사용량 증가

잠정 결론:
MCP 자체가 저부하 LLM 또는 embedding runtime을 갖지 않는 한, core가 의미 중복을 확정하는 것은 과하다. 대신 `duplicate candidates`를 deterministic하게 제시하고, 최종 판단은 사용자/AI가 하도록 두는 방식이 적절하다.

이는 sqlite activity index의 확장 후보로 볼 수 있다. `elf similar <text>` 또는 `entry_new` 전에 후보를 warning으로 보여주는 UX는 가능하지만, hard block은 피해야 한다.
