## multi-vault 호출 정책 정리: 생략 시 local-first, 명시 시 alias 강제 접근 (2026-04-24)

사용자 제안을 반영하여 향후 tool 호출 단위 `vault` 파라미터의 정책을 더 간결하게 정리함.

### 1. `vault` 생략 시: local 우선 + 기존 fallback 룰

tool 호출에서 `vault`를 생략한 경우 기본 동작은 local 우선이어야 한다. 즉 현재 세션/프로세스가 인지한 local vault가 있으면 이를 사용하고, 없으면 기존 fallback 룰을 적용한다.

기존 fallback 룰은 `--vault`/primary 지정, `ELF_VAULT`, CWD 상위 탐색, global fallback 등 현재 구현된 경로 결정 흐름을 의미한다. 중요한 것은 자동 선택 자체보다, 선택 결과가 반드시 응답에 기록되어야 한다는 점이다.

따라서 모든 tool 응답은 상시 `vault`, `vault_kind` 또는 equivalent resolved vault 정보를 포함해야 한다. 그러면 기본값이 local이든 fallback global이든, 에이전트와 사용자가 실제 참조 경계를 확인할 수 있으므로 안전성이 높아진다.

### 2. `vault` 명시 시: alias/예약어로 강제 접근

사용자가 필요할 때는 tool 호출에 `vault` 값을 명시하여 특정 vault에 강제로 접근할 수 있어야 한다.

예상 형태:
- `vault = "global"` — global vault 강제 접근
- `vault = "local"` — 세션 local vault 강제 접근
- `vault = "<alias>"` — 등록된 vault alias 접근
- `vault = "D:\\path\\to\\repo"` — 절대경로 일회성 접근

이 경우 fallback 추론을 하지 않고 명시된 대상만 resolve한다. resolve 실패 시 다른 vault로 자동 대체하지 말고 에러를 반환해야 한다.

### 안전성 원칙

- 기본 호출은 local-first로 편하게 둔다.
- 예외 참조는 alias/예약어로 명시한다.
- 모든 결과에는 resolved vault 출처를 포함한다.
- 명시 접근 실패 시 fallback하지 않는다.

이 조합이면 Codex처럼 repo CWD가 살아 있는 host에서는 자연스럽게 local-first가 동작하고, Claude Desktop처럼 CWD가 끊긴 host에서는 사용자가 alias/예약어로 명시 접근할 수 있다. 어느 경우든 응답의 출처 기록이 오염 감지 장치로 작동한다.
