## multi-vault 호출 정책 리스크 분석 (2026-04-24)

N0038 r0009의 "vault 생략 시 local-first, 명시 시 alias 강제 접근, 모든 응답에 출처 포함" 정책에 대한 리스크와 보완 제안을 정리함.

### 긍정적 평가

이 정책은 기본 사용성과 명시적 제어를 잘 분리한다. 일반적인 repo 작업에서는 사용자가 매번 `vault`를 지정하지 않아도 local-first로 자연스럽게 동작하고, global이나 다른 vault가 필요할 때만 alias/예약어를 명시하면 된다. 또한 모든 응답에 resolved vault 출처를 포함하면, host-specific CWD 차이나 잘못된 primary 선택을 사후 확인할 수 있다.

### 주요 리스크

1. 조용한 global fallback
`vault` 생략 시 기존 fallback 룰을 적용하면, local vault가 없거나 host CWD가 어긋난 상황에서 global이 선택될 수 있다. 응답에 출처가 표시되더라도 에이전트가 이를 매번 주의 깊게 읽지 않으면 사용자는 local 작업 중이라고 착각할 수 있다.

2. local의 의미 불안정
Codex처럼 repo 기준 세션에서는 `local`이 명확하지만, Claude Desktop처럼 고정 앱 컨텍스트에서는 `local`이 사용자가 생각하는 repo가 아닐 수 있다. 따라서 `local` 예약어는 반드시 session local 등록이 있을 때만 의미를 갖게 하는 편이 안전하다.

3. alias 오염 또는 stale alias
config `[vaults]`에 등록된 alias가 오래되어 다른 경로를 가리키거나, 이름이 충돌할 수 있다. alias resolve 결과 역시 응답에 절대경로로 표시해야 하며, write 작업에서는 alias를 사람이 검토할 수 있어야 한다.

4. 명시 접근의 쓰기 위험
`vault="global"` 또는 외부 alias를 지정한 상태에서 `revision_add`, `entry_new` 같은 write tool을 호출하면 global/타 vault 오염이 가능하다. 읽기 override와 쓰기 override는 동일하게 취급하면 위험하다.

5. 에이전트의 출처 무시
출처를 반환해도 에이전트가 작업 요약이나 판단 근거에 반영하지 않으면 안전장치 효과가 약해진다. 도구 응답뿐 아니라 tool description/session_start instruction에서 출처 확인을 작업 프로토콜로 강조해야 한다.

### 보완 제안

- `vault` 생략 + resolved `vault_kind = global`인 경우 응답에 `fallback: true` 또는 `warning` 필드를 포함한다.
- `session_start`에서 `expected_local` 또는 `local_vault` 등록을 지원하고, 등록된 local이 있을 때만 `local` 예약어를 resolve한다.
- read tool은 alias/절대경로 override를 허용하되, write tool은 external/global 대상일 때 `confirm` 또는 별도 플래그를 요구한다.
- 모든 응답에 `vault`, `vault_kind`뿐 아니라 가능하면 `vault_resolution`(`explicit`, `session_local`, `primary`, `fallback_global`, `alias`)을 포함한다.
- sync_record에는 세션에서 사용한 주요 vault 출처를 함께 남길 수 있으면 사후 감사가 쉬워진다.

### 결론

정책의 기본 방향은 타당하다. 다만 안전성의 핵심은 단순히 출처를 반환하는 것에서 한 단계 더 나아가, 조용한 fallback과 외부/global write를 눈에 띄게 만드는 데 있다. 특히 Claude Desktop류 host에서는 local CWD 추론을 신뢰하기 어렵기 때문에 `session_start(local_vault=...)`와 `vault_resolution` 메타데이터가 중요하다.
