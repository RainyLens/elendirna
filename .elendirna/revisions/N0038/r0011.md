## 보완 제안 상세 검토: warning/fallback, reserved alias, vault_resolution, write confirm, sync alias 기록 (2026-04-24)

N0038 r0010의 보완 제안에 대한 사용자 코멘트를 바탕으로 적용/미적용 판단을 구체화함.

### 1. `warning` 또는 `fallback: true`가 아니라 AND

사용자 의견처럼 OR보다 AND가 더 안정적이다. `fallback: true`는 기계가 안정적으로 판별할 수 있는 구조화 신호이고, `warning`은 사람과 에이전트가 의미를 놓치지 않도록 하는 설명 신호다.

권장 응답 형태:
```json
{
  "vault": "C:\\Users\\...",
  "vault_kind": "global",
  "fallback": true,
  "warning": "No local vault was resolved; using global vault fallback."
}
```

특히 MCP host가 Claude Desktop처럼 CWD 의도를 잃기 쉬운 경우, 구조화 필드만 있으면 사람이 못 보고, warning만 있으면 에이전트/테스트가 못 잡을 수 있다. 따라서 둘을 함께 반환하는 편이 좋다.

### 2. 예약 키워드를 alias처럼 선점하는 정책

원래 의도처럼 `local`, `global` 같은 키워드를 일반 alias와 같은 네임스페이스에서 선점하는 방향은 타당하다. 다만 현재 필요한 예약어는 `local`, `global` 정도로 보이며, 과도한 선점은 향후 사용자의 alias 선택 자유를 줄일 수 있다.

권장안:
- 지금은 `local`, `global`만 hard-reserved.
- `primary`, `default`, `session`, `cwd`, `parent` 같은 후보는 문서상 reserved candidates로만 남기고 실제 선점하지 않는다.
- alias 등록 시 `local`/`global`은 거부한다.
- 응답에는 alias뿐 아니라 resolved absolute path를 함께 표시한다.

적용 장점:
- `vault="global"`의 의미가 어느 환경에서도 안정적이다.
- 사용자가 실수로 global/local alias를 덮어쓰는 사고를 막는다.
- 구현과 문서가 단순하다.

미적용 장점:
- alias 네임스페이스가 완전히 사용자 자유로 남는다.
- 예약어 확장에 따른 호환성 부담이 없다.

판단: 현재는 `local`/`global`만 적용하는 것이 가장 균형이 좋다. `parent` 등은 실제 필요성이 입증되기 전까지 미적용 권장.

### 3. `vault_resolution` 설명: 무엇을 선택했는가와 왜 선택했는가의 분리

현재 `vault`, `vault_kind`는 "최종적으로 어느 vault를 봤는가"를 알려준다. 하지만 안전 진단에는 "왜 그 vault가 선택됐는가"도 필요하다. `vault_resolution`은 이 선택 이유를 나타내는 필드다.

예시:
- `explicit`: 사용자가 `vault="global"`처럼 명시했다.
- `session_local`: session_start로 등록된 local vault가 기본값으로 선택됐다.
- `primary`: 서버 시작 시 고정된 primary vault가 선택됐다.
- `fallback_global`: local/primary 탐색 실패 후 global fallback이 선택됐다.
- `alias`: 등록 alias를 resolve해서 선택됐다.

이 필드가 있으면 같은 `vault_kind="global"`이라도 의미가 달라진다.
- 사용자가 `vault="global"`로 명시한 global: 정상적인 의도
- local을 기대했는데 fallback으로 잡힌 global: 경고 대상

따라서 더 안전한 조치는 단순히 출처를 보여주는 것이 아니라, 출처가 결정된 경로를 함께 보여주는 것이다. 사용자가 3번을 이해하기 어렵다고 느낀 부분은 이 필드가 추가 정보처럼 보이지만 실제로는 "의도적 global"과 "사고성 global"을 구분하는 핵심 진단값이라는 점에 있다.

### 4. global/external write confirm

사용자 의견에 동의. `vault="global"` 또는 외부 alias/절대경로를 대상으로 `entry_new`, `revision_add`, `entry_status`, `sync_record` 같은 write tool을 실행할 때는 confirm 또는 사용자 확인 절차가 필요하다.

권장 정책:
- read tool: explicit vault 접근 허용
- write tool: 기본 local/primary 쓰기는 허용
- write tool + explicit global/external: `confirm=true` 요구 또는 에러 메시지로 사용자 확인 유도
- confirm 응답에도 resolved vault와 alias를 반드시 포함

### 5. sync_record에는 alias 수준 기록

사용자 의견처럼 sync_record에는 전체 절대경로보다 alias 수준 기록이 적절하다. 절대경로는 개인 환경 정보 노출 위험이 있고 로그가 장황해진다.

권장:
```json
"vault_refs": ["local", "global", "customer-a"]
```

단, 개별 tool 응답에는 디버깅과 안전 확인을 위해 resolved absolute path를 유지한다. 즉 실시간 응답은 상세하게, 장기 sync 로그는 alias 중심으로 간결하게 남긴다.
