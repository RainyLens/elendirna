## Delta

## reserved alias 후보 재검토: default와 parent (2026-04-24)

사용자가 `default`와 `parent` 예약어에 끌린다고 코멘트하여, 두 후보의 장단점을 별도로 검토함.

### `default` 후보

매력:
- 사용자가 "지금 기본으로 잡힌 vault"를 명시하고 싶을 때 직관적이다.
- `vault` 생략과 같은 의미를 명시적으로 표현할 수 있다.
- tool 호출 로그에서 `vault="default"`라고 남으면 "자동 기본값을 의도적으로 사용했다"는 신호가 된다.

리스크:
- `default`가 primary인지, session local인지, fallback 이후 결과인지 모호할 수 있다.
- `vault` 생략과 의미가 거의 같으면 API 표면만 늘어날 수 있다.
- fallback global까지 포함하는 default라면 안전성 측면에서 너무 관대하다.

권고:
- `default`는 hard-reserved candidate로 문서화하되 즉시 구현은 보류.
- 구현한다면 `vault_resolution="default"`가 아니라 실제 resolution(`session_local`, `primary`, `fallback_global`)을 함께 반환해야 한다.
- `vault="default"`는 "생략과 동일"으로만 정의하고 별도 resolve 의미를 만들지 않는 편이 안전하다.

### `parent` 후보

매력:
- nested repo/submodule/worktree 구조에서 상위 vault를 명시 참조할 수 있다.
- 프로젝트 내부의 하위 패키지에서 상위 monorepo vault를 보는 시나리오에 자연스럽다.
- 로컬 계층 구조를 표현하는 단어로 직관적이다.

리스크:
- Codex처럼 repo CWD가 명확한 host에서는 유용할 수 있지만, Claude Desktop처럼 CWD가 앱/관리 폴더인 host에서는 parent가 전혀 엉뚱한 의미가 된다.
- "현재 vault의 parent"인지, "현재 프로세스 CWD의 parent 탐색 결과"인지 정의가 애매하다.
- 보안 관점에서 parent 탐색은 의도보다 넓은 상위 경계를 열 수 있다.

권고:
- `parent`는 지금 선점하면 alias 충돌 방지 효과는 있지만, 의미 정의가 충분히 안정적이지 않다.
- 구현 전제는 session local 또는 explicit path가 있을 때만 parent를 계산하는 것.
- CWD 기반 parent는 host-specific 오작동 가능성이 크므로 지양.
- 따라서 `parent`도 hard-reserved candidate로만 남기고, 실제 필요가 생기면 `vault="parent"`보다 `vault="../"` 또는 explicit alias 등록으로 먼저 해결하는 것이 안전하다.

### 종합 판단

`default`와 `parent`는 둘 다 쓸모 있는 냄새가 있지만, 지금 당장 hard-reserved로 적용하면 의미 안정성보다 미래 가능성에 비용을 먼저 지불하는 꼴이 될 수 있다.

추천 단계:
1. 즉시 hard-reserved: `local`, `global`
2. 문서상 reserved candidate: `default`, `parent`, `primary`, `session`, `cwd`
3. alias 등록 시 candidate와 충돌하면 warning만 출력하고 허용할지, 아니면 future-reserved로 거부할지는 별도 결정

개인적인 선호는 `default`는 future-reserved로 강하게 남기고, `parent`는 아직 실사용 시나리오가 확인될 때까지 약하게 남기는 쪽이다. `default`는 API 표현력의 문제이고, `parent`는 경계 확장의 문제라 리스크 성격이 더 크다.
