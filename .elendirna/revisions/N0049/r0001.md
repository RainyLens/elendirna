## Delta

## 제안: publish draft workflow
`publish` 또는 `checkpoint`라는 이름으로 논의된 기능은 현재로서는 구현 확정보다 proposal로 둔다.

핵심 아이디어는 private vault의 raw context를 public artifact로 직접 노출하지 않고, 공개 가능한 문서/issue/RFC/patch 초안으로 승격하는 워크플로를 제공하는 것이다.

## 관찰
MVP 수준의 `publish`는 본질적으로 다음과 같다.

- `bundle`로 entry + revision chain + linked context를 수집한다.
- 여기에 "빈칸에 알맞게 이 내용을 정리해 넣으세요"에 해당하는 public-writing prompt/template을 붙인다.
- AI가 raw private context를 공개 가능한 산출물로 재작성한다.

즉, 새 저장 구조나 AI 내장 기능이 아니라 `bundle + prompt template`에 가까운 얇은 wrapper다.

## 용도
이 기능은 일반 사용자용 대중 기능이라기보다, 현재 Elendirna를 실제로 dogfooding하는 사람에게 먼저 유용하다.

- private vault insight를 public README/docs/RFC/issue로 승격
- 실무/개인 맥락이 섞인 raw revision을 그대로 공개하지 않도록 완충
- N0026 r0001 같은 near-miss를 방지하기 위한 review task 제공
- public canonical repo와 private workbench를 분리한 N0048 운영 모델을 보조

## publish와 checkpoint의 차이

- `checkpoint`
  - private vault 내부의 기준점 생성.
  - 긴 revision chain을 요약하거나 이후 `bundle --since` 기준점으로 사용.
  - public 공개와 직접 연결되지는 않음.

- `publish`
  - private → public 승격 준비.
  - raw bundle을 공개 가능한 artifact 초안으로 변환하도록 AI에게 task를 제공.
  - 공개 전 검토와 anonymization을 전제로 함.

현재 문제의식에는 `publish`가 더 직접적으로 맞는다.

## 가능한 인터페이스

초기 후보:

```bash
elf publish N0047 --format rfc
elf publish N0047 --format issue --output docs/rfcs/0047-bundle-policy.md
```

또는 bundle 확장 후보:

```bash
elf bundle N0047 --prompt publish-rfc
```

MCP에서는 `bundle` 결과에 publish prompt를 결합하는 workflow prompt로 구현할 수도 있다.

## 원칙

- CLI는 AI API를 직접 호출하지 않는다.
- `publish`는 실제 공개가 아니라 public draft 생성/검토 task다.
- raw private note를 그대로 복사하지 말고, 민감/실무/개인 맥락을 제거하거나 일반화하도록 명시한다.
- 결과물은 사람이 검토한 뒤 public repo에 반영한다.

## 보류 이유
아직 이 기능은 Elendirna를 직접 dogfooding하는 사람 외에는 용도가 명확하지 않다. 따라서 현 시점에서는 구현 항목이 아니라 proposal로 유지하고, 실제 반복 사용 사례가 더 쌓이면 MVP를 정한다.
