## Delta

# Scenario: 로컬 repo 코드 작업 중 global vault의 업무 지식 참조

## 배경

개발자는 특정 고객사/도메인 프로젝트의 로컬 repo에서 코드 작업 중이다. 이 repo에는 프로젝트 전용 local vault가 있으며, 현재 작업 대상 파일과 구현 결정, repo 내부 설계 기록은 local vault에 남긴다.

하지만 일부 비즈니스 로직은 repo 안의 문서만으로는 판단할 수 없다. 예를 들어 정산 정책, 계약별 예외, 내부 운영 규칙, 고객사별 금칙 조건 같은 지식은 여러 프로젝트에 걸쳐 재사용되는 global vault에 있다.

## 대표 상황

사용자가 에이전트에게 요청한다:

> 이 결제 취소 로직을 고쳐줘. 단, 우리 회사의 B2B 환불 정책과 VIP 고객 예외 규칙을 반영해야 해.

에이전트는 먼저 local vault에서 현재 repo의 아키텍처와 변경 이력을 확인한다. 이후 비즈니스 규칙 자체는 global vault에서 명시적으로 조회한다.

예상 흐름:

1. `session_start`로 현재 local vault가 `D:/code_etc/<repo>`임을 확인한다.
2. local vault에서 `query(tag='payment')`, `bundle(N####)` 등으로 repo-local 구현 맥락을 읽는다.
3. global vault에서 `query(vault='global', tag='refund-policy')` 또는 `bundle(vault='global', id='N####')`로 공통 비즈니스 규칙을 읽는다.
4. 코드 변경은 repo 작업공간에 수행한다.
5. 작업 기록과 구현 판단은 local vault에 `revision_add` 또는 `entry_new`로 남긴다.
6. global vault에는 원칙적으로 쓰지 않는다. 단, 업무 규칙 자체가 바뀌었거나 누락이 발견된 경우에만 사용자의 명시 요청 후 global vault에 별도 revision을 남긴다.

## 핵심 요구사항

### 1. global 접근은 명시적이어야 한다

로컬 repo에서 작업 중일 때 기본 대상은 local vault다. global vault 접근은 `vault='global'`처럼 tool 호출에 명시되어야 한다. CWD나 MCP primary vault에 의해 암묵적으로 global이 선택되면 안 된다.

### 2. 모든 응답은 출처를 포함해야 한다

global vault에서 읽은 정책과 local vault에서 읽은 구현 맥락이 섞이면 위험하다. `bundle`, `query`, `entry_show` 응답에는 `vault`, `vault_kind`가 포함되어야 하며, 에이전트는 답변과 기록에서 어떤 판단이 global 지식에 근거했는지 구분할 수 있어야 한다.

### 3. write boundary는 local-first다

로컬 repo 코드 작업의 결과물은 local vault에 기록한다. global vault는 업무 규칙의 출처이며, 코드 작업 로그의 저장소가 아니다.

금지되는 흐름:
- global vault에서 정책을 읽은 뒤, 코드 작업 요약을 global vault에 기록
- local vault에 남겨야 할 repo-specific 결정을 global vault에 revision으로 추가
- global 정책을 임의로 해석해 global vault의 원문을 수정

허용되는 흐름:
- global vault에서 `B2B 환불 정책`을 읽고 local vault의 `결제 취소 로직 변경` entry에 참조로 남김
- global 정책에 모순이나 누락이 발견되면 사용자 확인 후 global vault에 `정책 보완 필요` revision 추가

## 보안 및 품질 관점

이 시나리오는 multi-vault 기능이 단순 편의 기능이 아니라 업무 로직의 신뢰 경계임을 보여준다.

- local vault: repo-specific 구현 맥락, 코드 변경 이력, 기술적 판단
- global vault: 조직/개인 전체에 걸친 정책, 도메인 지식, 재사용 가능한 업무 규칙

둘을 동시에 읽을 수 있어야 하지만, 쓰기 대상과 출처 표시는 반드시 분리되어야 한다.

## 제품적 의미

Elendirna가 AI 코딩 보조 도구의 메모리 계층으로 쓰일 때, local vault만으로는 부족하다. 실제 업무 코드는 repo-local 설계와 global business rule이 함께 작동하기 때문이다.

따라서 MCP multi-vault는 다음 워크플로를 지원해야 한다:

- local repo에서 개발 중인 에이전트가 global vault의 업무 지식을 안전하게 조회
- 조회한 global 근거를 local 작업 기록에 출처와 함께 남김
- global vault 오염 없이 repo-specific 변경을 local vault에 보존
- 필요한 경우에만 사용자 승인 하에 global 업무 지식 자체를 갱신
