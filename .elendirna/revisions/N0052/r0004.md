## Delta

## v0.5 범위 밖 후보: 중복 기록 후보 탐지 (2026-04-24)

사용자 관찰에 따라 중복 기록 탐지는 유용하지만 v0.5 확정 스코프에서는 제외한다.

문제:
- 기록하려는 내용이 이미 다른 entry/revision에 있는지 확인하고 싶다.
- 하지만 의미 중복 판단은 MCP 자체에 저부하 LLM/embedding 계층이 없는 한 정확히 하기 어렵다.

v0.5 판단:
- multi-vault, 첨부파일, sync_record 역직렬화가 우선이다.
- 중복 탐지는 제품적으로 유용하지만 별도 검색/인덱싱/AI 판단 계층이 필요하므로 후속 후보로 둔다.

후속 후보:
- sqlite FTS 기반 `similar`/`search` 후보 제시
- entry 생성 전 title/tag 기반 duplicate warning
- MCP `query` description에서 기록 전 후보 검색을 soft steering
- 외부 AI가 query/bundle 결과를 보고 중복 여부를 판단하는 workflow

원칙:
- 중복 후보는 제시하되, core가 의미 중복을 확정하거나 기록을 hard block하지 않는다.
- Elendirna는 deterministic index + AI/human judgment 조합을 우선한다.
