## v0.5 구현 세부 정책 결정: sync warning, AI 선택, asset key affix (2026-04-24)

사용자와 v0.5 구현 세부 정책을 추가로 정리했다.

### 1. attach/detach의 sync event 실패 처리

정책: warning이 적절하다.

근거:
- sync는 핵심 source of truth가 아니라 보조 활동 로그/AI handoff hint다.
- attach/detach의 핵심 결과는 assets 파일과 manifest.sources 변경이다.
- sync event 기록이 실패해도 vault의 작동상 핵심 문제는 없다.

따라서 attach/detach에서 파일 조작과 manifest 갱신이 성공했다면, sync event 기록 실패만으로 전체 작업을 실패시키지 않는다. 대신 API result에 warning을 포함한다.

### 2. external/global write confirm UX

정책: 지나치게 강제하지 않고 AI/클라이언트 선택에 맡기는 방향이 좋다.

해석:
- global/external write는 위험 신호를 충분히 반환한다.
- 다만 항상 confirm gate로 막으면 AI 행동 강박성과 UX 마찰이 커질 수 있다.
- Elendirna의 guidance 원칙상 강제보다 출처/위험 신호를 명확히 주고 선택은 사용자/AI에게 맡기는 쪽이 맞다.

구현 후보:
- 응답 또는 tool description에서 external/global write의 위험을 명확히 표시
- confirm hard gate는 보류하거나 optional policy로 둔다
- 모든 write 응답에 resolved vault 정보를 포함해 사후 확인 가능하게 한다

### 3. asset key 충돌 처리

정책: 중복 파일명/key가 있으면 affix 숫자를 붙여 고유 key를 만들고, API result schema에 최종 결과 파일명/asset_key를 반환한다.

예:
- 원본: `diagram.png`
- 기본 key: `N0021_diagram.png`
- 충돌 시: `N0021_diagram_2.png`, `N0021_diagram_3.png`

응답에는 최소한 다음을 포함한다.
- `asset_key`: manifest.sources에 등록된 최종 key
- `stored_filename`: 실제 assets 디렉터리에 저장된 파일명
- `source_path`: 원본 경로
- `collision`: 충돌로 인해 이름이 변경되었는지 여부
- `requested_name` 또는 `original_name`: 사용자가 요청/원본 파일명

판단:
이 방식은 클라이언트가 충돌 해결 로직을 알 필요 없이, 서버가 최종 이름을 결정하고 결과를 명시한다는 점에서 좋다. AI/MCP client는 반환된 `asset_key`만 이후 detach/assets/show에 사용하면 된다.
