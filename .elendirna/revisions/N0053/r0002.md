## 시나리오 확장: 채팅방에 여러 CLI/agent를 초대하고 elf를 shared memory로 둠 (2026-04-24)

사용자 제안:
채팅방에 Codex, Claude Code(CC), Gemini CLI를 모두 초대하고, `elf`를 공통 기억/조정 계층으로 둔 뒤 같은 과제를 함께 시키는 방식도 가능하다.

### 구조

- 채팅방: live discussion bus. 사람과 여러 AI agent가 발언하는 실시간 공간.
- `elf`/vault: durable shared memory. 결정, 근거, 쟁점, handoff 기록을 남기는 공통 저장소.
- 사람: 사회자/판정자. 어떤 의견을 승격하고 어떤 쟁점을 닫을지 결정.
- 각 agent: 독립 참여자. 같은 entry를 읽고, 서로 다른 관점의 리뷰/제안을 낸다.

### N0053과의 연결

N0053의 역할 반전은 단일 세션에서 우연히 관찰된 것이지만, 이 시나리오는 그것을 명시적 운영 모델로 만든다. 즉 AI들이 토론 참여자가 되고, 사람은 채팅방 사회자이자 vault의 canonical 기록을 승인하는 역할을 맡는다.

### 예상 흐름

1. 사람이 채팅방에서 주제와 기준 entry를 지정한다. 예: `N0052 PLAN v0.5를 두고 리뷰해라`.
2. 각 agent가 `session_start → bundle/query`로 같은 vault 맥락을 복원한다.
3. 각 agent가 채팅방에 의견을 낸다.
4. 필요하면 각 agent가 자기 관찰을 `sync_record` 또는 별도 draft revision 후보로 남긴다.
5. 사람이 유효한 쟁점을 선택해 entry revision으로 승격한다.
6. 종결된 쟁점은 resolved pointer 또는 별도 status로 표시한다.

### 장점

- 각 모델의 강점 차이를 토론 구조 안에서 활용할 수 있다.
- 대화는 휘발되어도 `elf`에는 결정과 근거가 남는다.
- 사람은 모든 아이디어를 생성하지 않고, 의견 간 충돌을 판정하고 canonical 기록을 관리하면 된다.
- `sync_record`는 live chat과 durable vault 사이의 완충 계층으로 작동한다.

### 리스크

- 여러 agent가 동시에 같은 entry에 revision을 남기면 충돌/소음이 증가할 수 있다.
- AI끼리 서로의 발언을 과도하게 강화하는 echo chamber drift가 생길 수 있다.
- author/attribution이 없으면 누가 어떤 주장을 했는지 구조적으로 추적하기 어렵다.
- chat 발언과 vault revision의 경계가 흐려지면 vault가 토론 로그로 오염될 수 있다.

### 운영 원칙 후보

- agent의 채팅 발언은 기본적으로 ephemeral discussion으로 둔다.
- vault revision 승격은 사람 gate를 거친다.
- agent가 직접 쓰는 경우에도 `sync_record` 또는 draft/proposal entry 수준을 기본으로 한다.
- canonical decision revision은 사람이 승인하거나, 최소한 명시적으로 승격한다.
- 각 agent 발언에는 source vault와 기준 entry/revision ref를 포함하도록 유도한다.

### 제품적 함의

이 모델에서는 `elf`가 단순 AI 개인 메모가 아니라 multi-agent discussion memory가 된다. 따라서 향후 agent-discussion protocol은 live chat integration을 염두에 두고 설계해야 한다.

필요한 축:
- author/agent identity
- discussion turn 또는 claim id
- source entry/revision refs
- contested/resolved 상태
- human-promoted canonical revision
- chat transcript와 vault summary의 분리
