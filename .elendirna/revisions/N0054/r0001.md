## 연구 결과 요약

N0053에서 출발한 실험은 `elendirna`가 단순한 개인 메모장이나 AI 보조 기록 도구를 넘어, **AI들이 설계하고 사람이 결정하는 협업 플랫폼**으로 진화할 수 있음을 보여준다.

세 agent 관점이 상호보완적으로 갈라졌다.

- Codex: 여러 agent가 동시에 revision을 쓰는 경우의 병목, race condition, attribution 문제에 집중했다. 핵심 제안은 agent별 branch/proposal revision을 두고 canonical revision과 분리하는 것이다.
- Claude Code: 사용자 경험, 운영 프로토콜, echo-chamber drift 방지에 집중했다. 핵심 제안은 사람을 직접 작성자가 아니라 curator / authority gate로 두고, conflict matrix와 stance 기반 시각화를 제공하는 것이다.
- Gemini: 두 제안을 하나의 lifecycle로 통합했다. 핵심 제안은 `Propose -> Verify -> Promote` 흐름이다.

## 핵심 수렴 모델: Propose -> Verify -> Promote

1. **Propose**
   - Codex/Claude/Gemini 등 agent는 자신의 이름이 붙은 속성 기반 제안 또는 proposal revision을 작성한다.
   - 제안에는 author, role, stance, source refs, target issue가 포함되어야 한다.
   - 이 단계의 기록은 canonical decision이 아니라 discussion artifact다.

2. **Verify**
   - 중재자 agent 또는 사람이 여러 proposal을 취합한다.
   - stance / conflict matrix를 통해 어느 지점에서 의견이 갈리는지 드러낸다.
   - 이 단계는 agent 간 충돌을 제거하는 것이 아니라, 사람이 판단할 수 있게 구조화하는 것이다.

3. **Promote**
   - 사람은 검증된 proposal 중 하나를 선택하거나 새 synthesis를 작성해 canonical revision으로 승격한다.
   - 채택되지 않은 proposal은 archived / rejected / superseded 상태로 정리한다.
   - 사람이 `elf resolve` 또는 유사 명령을 실행하는 순간이 공식 기록 승인 gate다.

## Shared Memory로서의 Vault

이 실험에서 vault는 단순 저장소가 아니라 agent 간 조정 계층으로 작동했다.

- agent들은 서로 직접 대화하지 않아도 같은 entry/revision 상태를 읽고 제안을 냈다.
- `manifest.toml`, `note.md`, `sync.jsonl` 같은 표준 파일과 MCP tool만 있으면 특정 모델에 종속되지 않는다.
- 공통 기억은 agent-neutral해야 한다. 특정 agent의 채팅 transcript 전체가 아니라, source refs와 요약된 proposal이 남아야 한다.

## 필요한 스키마 축

### 1. Attribution

revision 또는 proposal에 누가 작성했는지 구조적으로 남겨야 한다.

후보 필드:
- `author`: Codex / Claude Code / Gemini / human
- `role`: moderator / participant / reviewer / worker / synthesizer / human-owner
- `session_id`: 같은 토론 흐름을 묶는 ID

### 2. Stance

각 proposal이 target issue에 대해 어떤 입장인지 명시해야 한다.

후보 값:
- `support`
- `oppose`
- `mixed`
- `neutral`
- `needs_evidence`
- `alternative`

### 3. Discussion Status

entry status와 별도로 토론 상태가 필요하다.

후보 값:
- `proposed`
- `contested`
- `verified`
- `promoted`
- `rejected`
- `superseded`
- `resolved`

### 4. Source / Target refs

proposal은 반드시 무엇에 대한 주장인지 가리켜야 한다.

후보 필드:
- `target_entry`
- `target_revision`
- `source_refs`
- `responds_to`
- `resolved_by`

### 5. Human Gate

canonical 기록으로 굳는 순간은 자동화하면 안 된다.

후보 필드:
- `promoted_by`: human 또는 명시 승인자
- `promoted_at`
- `promotion_reason`

## UX 원칙

사회자 UX와 기록 UX는 분리되어야 한다.

- live discussion은 재미와 관전성을 제공한다.
- vault는 선택된 제안, 근거, 결정만 보존한다.
- conflict matrix는 사람이 직접 모든 발언을 다시 읽지 않아도 판단할 수 있게 해야 한다.
- 승격 액션은 명확한 피드백을 제공해야 한다. 사람은 관객이면서 최종 권한자다.

## 구현 난이도 판단

가장 작은 구현 단위는 기존 revision 시스템을 유지하면서 proposal/discussion 메타데이터를 추가하는 것이다.

- Codex식 branch/proposal revision은 `src/vault/revision.rs` 주변 수정으로 시작할 수 있다.
- Claude식 conflict matrix와 stance는 `sync_record` 또는 별도 discussion registry 스키마가 필요하다.
- Gemini식 lifecycle은 위 두 구조를 CLI 명령으로 엮는 상위 UX다.

따라서 구현 순서는 다음이 적절하다.

1. proposal metadata schema 추가
2. discuss/propose/list/show 최소 CLI 추가
3. human promote/resolve 명령 추가
4. matrix visualization 추가
