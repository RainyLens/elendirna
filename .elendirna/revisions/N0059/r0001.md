# v0.5 사후강평 - Codex 관점

## 작업 계획 대비 실제 결과

원래 계획은 Phase 2(첨부파일 MVP)와 Phase 3(sync_record entries 개선)의 구현 내용을 검수하고, 위험한 부분이 있으면 최소 보완하는 것이었다.

실제 결과는 다음과 같다.

- Phase 2 attachment MVP에서 파일 복사/충돌/해제 로직의 안전성을 보완했다.
- Phase 3 FlexibleEntries 역직렬화는 정책에 맞게 관대한 입력 수용과 명백한 불가 타입 거부를 분리했다.
- 관련 테스트를 추가했고 `cargo check`, `cargo test` 전체 통과까지 확인했다.

즉 기능 결과물은 목표에 도달했다. 다만 작업 운영은 깔끔하지 않았다.

## 보완된 점

### attachment copy/key safety

`src/vault/ops.rs`에서 다음 위험을 줄였다.

- `copy_name`이나 source filename이 path처럼 들어와 asset path에 영향을 주는 문제
- assets 파일은 없지만 manifest.sources에 이미 등록된 key를 재사용하는 문제
- 기존 파일을 덮어쓸 수 있는 복사 방식
- detach 후 더 이상 참조되지 않는 asset 파일이 orphan으로 남는 문제

보완 내용:

- 파일명은 단일 filename으로 정규화한다.
- source path는 일반 파일만 허용한다.
- 충돌 판단은 파일 시스템뿐 아니라 모든 entry의 `manifest.sources`까지 본다.
- 저장은 `create_new(true)`로 수행해 기존 파일 덮어쓰기를 피한다.
- detach는 다른 entry가 참조하지 않는 경우 실제 asset 파일도 삭제한다.

### FlexibleEntries

`src/mcp/mod.rs`의 `FlexibleEntries`는 N0041의 정책과 맞게 조정했다.

허용:

- JSON array
- 단일 문자열
- comma-separated string
- stringified JSON array

거부:

- number
- bool
- object

핵심은 sync_record.entries가 보조 handoff hint이므로 합리적으로 해석 가능한 입력은 관대하게 받되, 명백히 해석 불가능한 타입은 조용히 빈 배열로 삼키지 않는 것이다.

## 빼먹은 점 / 남은 리스크

### attach의 원자성은 아직 완전하지 않음

현재는 파일 생성 후 manifest write가 실패하면 방금 생성된 asset 파일이 orphan으로 남을 수 있다. MVP에서는 허용 가능한 수준이지만, 더 엄밀하게 하려면 manifest write 실패 시 best-effort rollback이 필요하다.

### 동시 writer 경쟁은 완전 처리하지 않음

충돌 검사 후 `create_new(true)`로 저장하므로 덮어쓰기는 막지만, 검사와 생성 사이에 다른 writer가 같은 key를 만들면 재시도 대신 오류가 날 수 있다. 로컬 CLI/MCP MVP에서는 큰 문제는 아니지만, 다중 writer를 고려하면 `AlreadyExists` 발생 시 affix 증가 후 재시도하는 루프가 더 좋다.

### warning surface 부족

FlexibleEntries 내부에서 stringified JSON array에 비문자열이 섞이면 현재는 해당 값만 버린다. 정책상 best-effort로 볼 수 있지만, API가 warning을 반환할 수 있다면 클라이언트에게 더 투명하게 알릴 수 있다.

## 작업 운영 강평

결과물 자체는 유효했지만 진행 방식은 일부 미흡했다.

### 잘못한 점 1: 전체 cargo fmt 실행

이미 작업 트리에 변경 파일이 많은 상태에서 `cargo fmt`를 전체 실행했다. 이 때문에 내 논리 변경과 기존 변경의 포맷 변화가 diff에서 섞였다.

검수 작업에서는 대상 파일만 포맷하거나, 최소한 실행 전후 diff 범위를 더 엄격히 분리했어야 한다.

### 잘못한 점 2: cargo test 병렬 실행

Windows 환경에서 `cargo test`를 여러 개 병렬로 실행해 target 디렉터리 파일 락 충돌을 만들었다. 이후 escalated 단일 실행으로 회복했지만, 불필요한 잡음이었다.

Rust 테스트는 이 환경에서는 순차 실행이 맞다.

### 잘못한 점 3: 기존 변경과 내 보완의 경계 표시 부족

작업 트리가 이미 큰 상태였기 때문에, 어디까지가 기존 Phase 2/3 구현이고 어디부터가 Codex 보완인지 중간 보고에서 더 명확히 선을 그었어야 한다.

최종 요약에서는 구분했지만, 작업 도중에는 diff 오염과 테스트 잡음 때문에 추적성이 나빠졌다.

## 결론

v0.5 Phase 2/3 검수 결과, 핵심 구현 방향은 타당했고 Codex 보완으로 attachment key safety와 FlexibleEntries strictness가 개선되었다.

다만 이번 Codex 작업 방식은 지나치게 넓은 포맷 실행과 병렬 테스트로 인해 운영 품질이 낮았다. 다음 유사 작업에서는 다음 원칙을 적용한다.

- 검수 작업에서는 먼저 변경 범위를 고정한다.
- 포맷은 가능한 한 touched file 중심으로 제한한다.
- Windows/Rust 환경에서는 cargo test를 병렬로 여러 개 띄우지 않는다.
- 큰 dirty worktree에서는 내 변경과 기존 변경을 보고 단계마다 분리해서 설명한다.
