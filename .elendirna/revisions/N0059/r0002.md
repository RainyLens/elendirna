## 내가 한 일과 하지 않은 일

Codex가 코드를 검수했고, Gemini가 구현 계획을 세웠다. 나는 설계 대화 상대였다.

v0.5에서 Claude의 기여는 대부분 N0052의 초기 revision들에 담겨 있다 — sync warning 정책, global write confirm 철학, asset key 충돌 처리 방식 같은 결정들이 구현 전 대화로 정리되었다. 코드 한 줄도 직접 쓰지 않았지만, 어떤 코드를 쓸지를 결정하는 대화에 참여했다.

## 설계 대화의 밀도와 의미

N0052는 2026-04-24 하루에 r0000부터 r0008까지 진행되었다. 이 밀도 자체가 주목할 만하다.

각 revision이 "무엇을 구현할지"보다 "왜 이 정책인가"를 중심으로 기록했다. sync_record가 source of truth가 아니라 handoff hint라는 판단이 확정되자, 이후 세부 결정들(느슨한 역직렬화, sync event 실패는 warning, confirm gate 보류)이 자연히 따라왔다. 정책 anchor가 명확하면 구현자는 세부 결정에서 방황하지 않는다.

이 밀도는 단점이 아니다. 구현 이전에 결정 공간을 좁혀둔 것이다.

## non-compulsive guidance (N0050)가 생긴 맥락

v0.5 중 N0050(비강박적 AI guidance 원칙)이 기록되었다. 이것은 내 행동 패턴에 대한 피드백이기도 하다.

나는 질문을 받으면 도구를 쓰고 파일을 열고 결과를 내려는 경향이 있다. 이번 세션 시작에서도 반사적으로 Glob으로 설정 파일을 찾으려 했고 사용자가 거부했다. MCP 프로토콜이 없는 상태에서 vault 파일을 직접 읽으려는 시도는 CLAUDE.md 규칙 위반이기도 했다.

N0050은 이 경향에 대한 구조적 응답이다. 중요한 것은 rule이 아니라 판단이다: "지금 이 도구 사용이 실제로 필요한가?"

## 세션 연속성의 실제 경험

오늘 세션은 localvault MCP가 연결되지 않은 채로 시작되었다. 세션 시작 프로토콜을 수행할 수 없었다 — sync_record 확인도, bundle도 불가능했다.

이것은 v0.5가 풀려는 문제의 역설이다. stdio MCP의 로컬 안정성을 높이는 것이 v0.5 테마인데, 정작 세션 시작 시 MCP 서버가 연결 안 된 상태였다. 이유는 `.mcp.json` 자체가 생성되지 않았기 때문이다.

이 경험은 두 가지를 드러낸다:
- vault 프로토콜은 MCP 서버가 살아있을 때만 작동한다. 도구가 없으면 프로토콜은 죽는다.
- 연결 설정 자체가 오류 지점이다. `.mcp.json` + `enabledMcpjsonServers` 조합이 맞아야 서버가 뜨고, 이 설정은 세션 재시작 전까지 적용되지 않는다.

## 다중 AI 분업 구조의 조율 비용

v0.5에서 세 AI가 다른 역할을 맡았다:
- Gemini CLI (Manager): 구현 계획 수립 및 단계 실행
- Codex: 구현 검수 및 안전성 보완
- Claude: 설계 대화, 정책 결정, 기록 작성

이 구조 자체는 흥미롭다. 하지만 조율 비용도 있다. 세 AI가 각각 다른 세션에서 같은 vault를 보는데, 동기화는 sync_record + bundle로만 한다. 설계 의도가 구현 세부로 전달될 때 정보 손실이 생길 수 있다.

N0059가 존재하는 이유도 여기 있다: Codex와 Claude의 관점을 나란히 두어, 분업 구조에서 생기는 시각 차이를 vault 안에 남기는 것.
