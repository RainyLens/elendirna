## Delta

# Agent별 MCP 연결 상태 불일치와 CLI fallback 필요

## 관찰

v0.5 사후강평 entry를 Codex가 생성하고 sync_record까지 남긴 직후, Claude 쪽 MCP 연결이 끊겨 있음을 뒤늦게 발견했다.

이 사건은 단순히 한 agent의 MCP가 꺼졌다는 문제가 아니라, dogfooding 환경에서 "MCP 기반 shared work memory가 모든 agent에게 동일하게 사용 가능하다"는 암묵적 가정이 깨질 수 있음을 보여준다.

## 문제 성격

- Codex MCP는 정상 동작하여 entry/revision/sync_record 기록이 가능했다.
- Claude MCP는 끊겨 있어 같은 vault 맥락을 즉시 읽거나 이어받을 수 없었다.
- 사용자는 agent 간 handoff가 가능하다고 기대하지만, 실제 availability는 host/agent별로 다를 수 있다.
- 따라서 handoff 기록 완료와 후속 agent의 handoff 수신 가능성은 별개의 상태다.

## 추가 관찰: CLI fallback 힌트의 가치

사용자 코멘트:
도그푸딩 환경 개발이므로 MCP가 끊겼더라도 CLI 호출만 힌트로 제공됐으면 fallback은 가능했을 것이다.

즉 문제는 MCP disconnect 자체보다, disconnect를 감지했을 때 agent가 다음 행동으로 넘어갈 수 있는 fallback 안내가 부족하다는 점이다.

예:

```powershell
elf sync log --tail 5
elf query --title "v0.5"
elf bundle N0059
elf bundle N0060
```

또는 MCP tool 실패 시 다음처럼 안내할 수 있다.

- "MCP 연결이 끊겨 있습니다. 같은 vault에서 `elf sync log --tail 5`로 최근 handoff를 확인하세요."
- "관련 entry는 N0059/N0060이며, CLI fallback은 `elf bundle N0059`입니다."

## 제품적 함의

MCP는 primary path지만, Elendirna는 CLI-first 구조를 이미 갖고 있다. dogfooding 환경에서는 이 점을 적극 활용해야 한다.

필요한 개선 후보:

1. MCP tool 실패/부재 시 CLI fallback command를 문서와 tool description에 노출
2. `session_start` 응답에 "CLI fallback" 섹션 포함 검토
3. README/AGENTS/CLAUDE 가이드에 MCP unavailable 시 최소 복구 절차 추가
4. handoff 기록 시 관련 entry ID뿐 아니라 CLI로 복원하는 예시 command를 남기는 옵션 검토
5. `elf health` 또는 `elf mcp doctor` 같은 진단 명령 후보 검토

## 판단

이 기능은 일반 사용자에게는 debug/운영 편의 기능처럼 보일 수 있지만, dogfooding과 multi-agent handoff에서는 중요하다.

MCP 연결이 끊겨도 CLI가 살아 있으면 shared memory 자체는 죽은 것이 아니다. 문제는 agent와 사용자가 그 fallback 경로를 즉시 떠올릴 수 있느냐다.

따라서 v0.5 이후 개선 방향은 "MCP availability를 절대 가정하지 않고, CLI fallback 힌트를 항상 가까운 곳에 둔다"로 잡는 것이 적절하다.
