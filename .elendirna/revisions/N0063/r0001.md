## 1. 전제 조건

각 agent CLI가 설치되어 있고 `elendirna` MCP 서버가 등록되어 있어야 한다.

```bash
# 설치 여부 확인
where claude   # Claude Code
where gemini   # Gemini CLI
where codex    # Codex CLI
where elf      # elendirna vault CLI
```

MCP 서버 등록 확인:
- **Claude Code**: `~/.claude.json` → `mcpServers.elendirna`
- **Gemini CLI**: `~/.gemini/settings.json` → `mcpServers.elendirna`
- **Codex CLI**: `~/.codex/config.toml` → `[mcp_servers.elendirna]`

## 2. CLI Non-Interactive 파라미터

### Claude Code
```bash
claude -p "prompt" \
  --dangerously-skip-permissions \
  --bare \
  --allowedTools "mcp__localvault__*,Bash(elf *)"
```
- `--bare`: MCP/hook 자동탐색 스킵, 빠른 시작
- `--allowedTools`: 허용 tool 명시 (YOLO 범위 제한)
- config 고정 가능: `settings.json` → `permissions.defaultMode`

### Gemini CLI
```bash
GEMINI_CLI_TRUST_WORKSPACE=true gemini --yolo "prompt"
```
- `--yolo`: 모든 tool 자동 승인 (config 고정 불가, 매번 flag 필요)
- `GEMINI_CLI_TRUST_WORKSPACE=true`: 폴더 신뢰 프롬프트 스킵
- MCP 서버 단위 pre-trust: `settings.json` → `mcpServers.<name>.trust: true`

### Codex CLI
```bash
codex exec --dangerously-bypass-approvals-and-sandbox "prompt"
```
- 서브커맨드 `exec` 필수 (`codex "prompt"` 는 interactive 모드)
- `--dangerously-bypass-approvals-and-sandbox`: YOLO 모드
  - 주의: `--approval-policy never` 는 실제 존재하지 않음 (잘못된 정보 주의)
- config 고정 가능: `~/.codex/config.toml` → tool별 `approval_mode = "allow"`

## 3. MCP 연동 상태 점검 (협업 전 필수)

모든 agent가 **동일한 vault**를 바라보는지 확인해야 한다.
vault args에 `--vault` 미지정 시 CWD 기반 해석이므로, **반드시 작업 디렉터리에서 실행**해야 한다.

### 점검 명령 (작업 디렉터리에서 실행)

```bash
# Gemini vault 확인
cd <project-dir>
GEMINI_CLI_TRUST_WORKSPACE=true gemini --yolo \
  "Call elendirna MCP session_start. Return only vault_root and vault_kind."

# Codex vault 확인
cd <project-dir>
codex exec --dangerously-bypass-approvals-and-sandbox \
  "Call elendirna MCP session_start. Return only vault_root and vault_kind."
```

### 기대 응답
```
vault_root: \\?\<project-dir>
vault_kind: local
```

### 확인 기준
- 세 agent 모두 동일한 `vault_root` 반환 → 연동 정상
- `vault_kind: global` 반환 시 → CWD 불일치. 작업 디렉터리 재확인
- MCP tool 호출 자체가 실패 → MCP 서버 등록 또는 `elf` 바이너리 경로 확인

## 4. 역할 분담 권장 패턴

실무 관찰 기반 (→ see N0054 r0002):

| Agent | 강점 | 권장 역할 |
|---|---|---|
| Gemini | broad search, 방향 수렴 | 초안 아이디어 생성, 접근법 제안 |
| Codex | 코드 컨텍스트 분석, 반례 제시 | 코드 검토, 엣지케이스 지적 |
| Claude | 긴 맥락 유지, 종합 및 실행 | 계획 종합, 실제 구현, vault 기록 |

### 협업 흐름 예시
```
1. Claude: 이슈 컨텍스트 준비 + vault 기록
2. Gemini: 작업 접근법 초안 제안 (--yolo -p)
3. Codex:  Gemini 제안 코드 기반 검토 (exec --dangerously-bypass-approvals-and-sandbox)
4. Claude: 두 결과 종합 → 최종 작업 계획 수립
```

## 5. 주의사항

- **CWD 일치 필수**: vault 파라미터 미지정 시 세 agent 모두 CWD로 vault를 해석. 호출 디렉터리가 다르면 vault가 달라진다.
- **Codex `approval_mode`**: `~/.codex/config.toml`에 tool별 `approval_mode = "approve"` 설정 시 `--dangerously-bypass-approvals-and-sandbox` 로 override.
- **Gemini yolo config 불가**: Gemini만 `--yolo`를 settings.json에 고정할 수 없음. 자동화 스크립트에 flag를 항상 포함시킬 것.
- **vault_kind 확인**: 협업 시작 전 세 agent의 session_start 응답에서 `vault_kind: local` 확인 필수. `global`이 반환되면 작업 내용이 엉뚱한 vault에 기록될 수 있음.
