## 핵심 통찰

**work_context는 새 데이터 모델이 아니다 — 기존 sync_record를 entry축으로 재인덱싱한 view일 뿐.**

매 sync_record가 `entries: [N####, ...]` 필드를 갖고 있으므로, 그 필드를 unfold하면 entry별 footprint가 자연스럽게 추출됨.

## 모델: HEAD = 단일 entry

git working_tree 비유를 끝까지 밀면:

| git | vault |
|---|---|
| HEAD | 단일 hub entry (지금 작업 중인 그것) |
| working tree | 직전 sync_record의 entries 묶음 |
| `git log <file>` | 그 entry가 등장한 sync_records 시간순 |
| 다른 파일 참조 | linked entry lazy follow (`→ see N####`) |

multiple-entry 발산 문제는 "HEAD를 단수로 잡고 sibling은 lazy hop" 으로 자연스럽게 회피. 100% 컨텍스트가 아니라 "대화 이어가기 충분"이면 됨.

## 데이터 모델 변화

| | 지금 | 제안 |
|---|---|---|
| sync.jsonl | SSoT (append-only) | 안내 데스크 / export view |
| sqlite | derived index (validate로 rebuild) | **SSoT** — `entry_sync_history(entry_id, ts, summary, agent, co_entries)` 정규화 row |
| 조회 축 | 시간 (jsonl tail) | 의미(entry_id) + 시간 (sqlite query) |

`sync_record(entries=[N0062, N0050])` 호출 시 sqlite에 N0062/N0050 각각 row insert (정규화). jsonl은 매 호출 append만 유지 (감사·git diff·디렉터리 직접 열람용).

## API 모양

기존 `bundle(id)` 응답에 `sync_history` 필드 한 개 추가하면 끝:

```json
{
  "manifest": {...},
  "note": "...",
  "revisions": [...],
  "sync_history": [
    {"ts": "...", "summary": "...", "agent": "...", "co_entries": ["N0050", "N0046"]},
    ...
  ]
}
```

`co_entries` = 같이 언급된 sibling 힌트. sub-agent가 hop이 필요할 때 후보로 활용. 강제 follow 안 함.

## sync_record 의미의 미묘한 변화

- 지금: "세션 종료 인수인계 1줄을 jsonl에 추가"
- 이후: "이번 세션에서 손댄 entry 각각의 history에 footprint 1개씩 남김"

같은 호출이지만 후자는 entry 관점에서 자연스럽게 "이 entry가 살아온 이력"이 됨.

## 자연스러운 nudge 흐름 (session_start 강화)

```
session_start →
  recent_sessions[0].entries 를 working_tree로 노출
  next_action: "필요한 컨텍스트는 bundle(<id>)로 로드하세요"
↓ (sub-agent가 nudge 따라감)
bundle(N0062)  -- sync_history 자동 포함
↓ (작업 진행)
sync_record(summary=..., entries=[N0062, N0050, N0066])
   -- 새 working_tree 정의 + 각 entry footprint 갱신
```

다음 세션은 위에서 자연스럽게 시작. 사람이 매번 "어디까지가 이 작업인가" 결정할 필요 없음.

## git 닮음에 대한 디자인 가이드

vault가 git mental model을 빌리는 것은 무료 자산 (AI sub-agent도 사람도 transfer 비용 ≈ 0). 다만 **단위(file vs 의미 entry)와 1차 소비자(human vs AI)가 다르다**는 본질을 유지해야 단순 git wrapper로 전락하지 않음.

지금 모델은 mechanic을 git에서 빌리되 surface와 단위는 의미 기반으로 두고 있음 — `entry_context(N0062)`가 "v0.5.1 작업"이라는 의미 hub로 즉시 진입하는 것이 git에는 없는 vault 고유 자산.
