### 핵심 발견: 'local' 별칭의 MCP 시맨틱이 launch path로 fix됨

MCP 서버에서 `vault='local'` 처리는 `resolve_named_vault` 경유:
- `'local'` → `self.launch_resolution.path` 그대로 반환
- launch_resolution은 MCP 서버 기동 시점 1회 결정 (`resolve_vault_root` → cwd부터 상위 탐색 → 실패 시 home fallback)

→ **매 호출 cwd 재탐색 없음.** session_start(vault='local')도 같은 `resolve_named_vault('local')` 경유라 동일 launch path 캡처.

대조: CLI는 `resolve_vault_alias("local")` 경유 → 매 호출 cwd 재탐색 (`src/vault/mod.rs:95-104`). 같은 'local'이지만 시맨틱이 다름.

### CC Desktop에서의 함정

- CC Desktop이 MCP 서버를 띄울 때 process cwd = 사용자 홈 (또는 desktop 앱 path)
- launch 시 `find_vault_root(home)` → `~/.elendirna/` 폴백 → **launch_resolution = global vault**
- 이후 사용자가 다른 폴더에서 작업해도 process cwd 불변
- per-call `vault='local'` 명시해도 → launch_resolution (=global) 반환
- **결과: 사용자 의도 'local' = 실제 global. silent 글로벌 쓰기**

### N0067 가설 vs 코드 실측

| N0067 가설 | 실측 결과 |
|---|---|
| CC Desktop 세션 라이프사이클 잔존 | 부분적 — 세션이 아니라 launch_resolution 자체가 launch 1회 결정 후 mutable 아님 |
| cwd 자동 등록 부재 | **확인** — find_vault_root는 launch 1회만, 이후 호출은 launch path 재사용 |
| per-call override 로직 결함 | **부분 확인** — 코드상 작동하지만 'local' 별칭이 launch path로 정의되어 있어 의도 어긋남. override 자체보단 별칭 시맨틱 함정 |

### Fix 옵션 (우선순위 미정)

1. `resolve_named_vault('local')`에서 매 호출 cwd 재탐색 — **무의미**. MCP 서버 process cwd는 client 작업 컨텍스트와 무관 (MCP 서버는 띄워두고 client request만 받음)
2. `session_start(local_path=<absolute>)` 명시 파라미터 추가 — 사용자가 직접 등록. cognitive load
3. 현 시맨틱을 문서화하고 CC Desktop은 명시 path 권고 — 운용 가이드만으로 cover
4. MCP request에 client cwd 전달 — MCP 표준으로는 미지원

`session_start(vault=...)`에 절대 path 명시 가능하게 확장하면 (2)가 가장 깔끔. 'local' 별칭 의미는 보존하되 "register session local from explicit path"가 추가됨.
