## Delta

## [Change] 초기 본문 — 1.0 게이트로서의 plugin 경계 strategic frame

### 핵심 명제

Plugin 생태계 정립이 1.0의 마지막 조각인 이유는 기능이 더 갖춰져서가 아니라, **plugin 경계가 axiom의 전역 일관성을 검증하는 마지막 시험대**이기 때문.

- 본체 안에서만 정합적인 axiom = *지역적* 일관성
- plugin까지 통제하는 axiom = *전역적* 일관성
- 후자가 검증되어야 외부 확장에 견디는 系로 인정 → 그게 진짜 1.0

### 1.0 게이트의 정확한 정의: SDK readiness ≠ ecosystem maturity

1.0 게이트는 *"plugin이 몇 개 붙었는가"*가 아니라 *"plugin이 본체에 붙을 수 있는 접면이 단단한가"*.

- plugin 갯수·생태계 활성도 = 1.0 이후 자생적 변수, 사용자 통제 불가
- 사용자가 책임질 수 있는 것 = 접면 하나
- 접면이 외부 의존을 받아들일 만큼 단단해진 순간 = 1.0 박힐 순간

따라서 *"plugin 생태계 완성이 1.0의 목표"*는 약간 misleading — 1.0 시점에 완성되는 건 SDK 표면, 생태계 자체는 1.0 이후의 산물.

### Plugin 작업 = 본체 API의 자기 도그푸딩 (외부자 시점)

본체 안에서만 도그푸딩하면 *내부자의 시점*만 시험된다. plugin SDK 정의 과정 = 본체 API를 *외부자의 시점*으로 호출해 보는 작업. 본체 안에서만 쓸 때는 안 보이던 어색함이 plugin 작성자 시점에서 드러남.

이 발견은 plugin 작업 중에만 보이고, 1.0 직전에 청소하지 않으면 1.0 이후에는 부술 변경으로만 풀 수 있음. 자연스러운 순서:

1. Plugin SDK 정의 (외부자 도그푸딩으로 본체 비대칭 발견)
2. 본체 API 마지막 정합성 청소
3. 1.0 박기

### Plugin 경계 = 거절의 근거 (1.0 이후 axiom 보존 메커니즘)

- 1.0 이전: *"본체에 넣을까 말까"* 판단이 직관 의존, 거절 근거가 *"이건 본체스럽지 않다"* 수준
- 1.0 이후: plugin 경계가 *"본체에 넣지 않는다"*를 이론적으로 정당화 — *"plugin으로 충분히 표현 가능하므로 본체 영역이 아니다"*

동결의 본질은 변화하지 않는 것이 아니라 *변화의 방향을 거절할 근거가 명확해지는 것*. attractor field가 새 use case를 흡수와 거절을 *동시에* 할 수 있게 만드는 메커니즘이 plugin 경계.

- 본체: 매우 신중하게 (부술 변경 불가)
- Plugin: 자유롭게 (독립 진화 가능)
- 두 속도의 분리 = 1.0이 동결되면서도 살아 있게 해주는 구조

### [Impact] 1.0 이후 작업 결의 변화

- 1.0 이전: *"내 도구"*를 만드는 작업
- 1.0 이후: *"공유 가능한 도구의 책임자"*가 되는 작업

외부 사용자가 plugin을 만들고 새로운 use case를 가져오면 도구 제작자는 예상치 못한 사용을 마주함. 도그푸딩만으로는 안 보이던 결이 드러나고, 그게 *attractor field가 새 결을 흡수하는가, 거절하는가*의 진짜 시험. 1.0은 끝이 아니라 다음 단계의 시작점.
