## 5 차원

- 통합 shape: 외부 MCP / in-tree feature / library
- 소싱 모델: closed curated (elen-labs) vs open third-party
- 신뢰·보안: sudo 가드, signing, sandbox
- 버전 호환: elf core 변동에 따른 핀 비용
- 발견·배포

## 2 무거운 hinge (미결)

1. **shape 단일화 가능 여부** — mutator(C8)·non-mutator(C1·C4·C5)가 다른 shape를 강제. 단일 shape 비현실 가능성 높음 → ecosystem 정책도 shape별 다중화 강제될 수 있음.
2. **third-party 허용 여부** — closed/open 분기. closed면 신뢰·보안·발견 부담 작아짐.

## 잠정 결정 (사용자 명시, 2026-05-07)

### 빌트인 플러그인
일단 **없음**을 default. 굳이 넣는다면 C1(HTTP server) 또는 C2-계열(read-only wiki, 사실상 C5에 흡수) 정도.

### 사용자 노출 방식 — "플러그인" 개념 비노출
사용자 mental model에 "플러그인" 추상 노출 X. **CLI 서브커맨드 등으로 자연 기능처럼 유도**. 즉 ecosystem 내부 구조와 사용자 표면을 분리. 이건 hinge#2(third-party 허용)에도 영향 — open이라도 "사용자에겐 elf 기능으로 보이게" 일관 유지 필요.

### 신규 기능 설치 UX
`elf install <X>` 류 **CLI 패턴 선호**. 단 실제 구현은 미결:
- cargo install? npm? bun? 자체 registry?
- 단일 binary 다운로드 + 등록?
- 외부 MCP 서버 config 자동 추가? (→ see N0016 002-mcp-server-config-auto-add 인접)

→ **여러 방면 고민 필요** (사용자 명시).

### 오류 메시지
정리 필요. 단 본 ecosystem 트랙과 결 다름 — **별도 트랙**으로 분리. 본 entry 범위 외.
