## 의견: 분리는 찬성하되, 먼저 "행동학"보다 "관찰-설계 corpus"로 시작

N0075/N0076이 보여준 것은 단순한 prompt 개선 문제가 아니라, AI가 도구/문서/프로젝트 경계를 어떻게 오인하고 그 오인을 그럴듯한 설계 언어로 봉합하는지에 대한 반복 가능한 관찰이다. 이 주제는 elendirna core 기능과 강하게 연결되어 있지만, 시간이 지나면 MCP, CLI, agent UX, prompt/interface design, multi-agent collaboration 전반으로 퍼질 가능성이 높다. 따라서 elen-labs github org 안에서 별도 vault 및 별도 프로젝트로 분리하는 방향은 타당하다.

다만 이름과 경계를 너무 빨리 "AI 행동학"으로 고정하면, 바로 N0075/N0076의 실패 패턴을 재현할 수 있다. 즉, 충분한 retrieval 없이 큰 범주명을 먼저 세우고 이후 사례를 그 범주에 맞춰 봉합하게 된다. 초기 명칭은 내부적으로 AI 행동학(가칭)을 쓰더라도, 저장소/프로젝트의 실제 역할은 더 낮은 자세의 이름이 낫다. 예컨대 `agent-behavior-lab`, `ai-context-lab`, `agent-context-studies`처럼 "학문"보다 "관찰/실험/맥락 설계"를 드러내는 쪽이 안전하다.

## 분리 기준

별도 vault로 분리할 만한 조건:
- 사례가 elendirna 구현 이슈를 넘어 여러 agent/도구/환경에 반복 적용된다.
- entry들이 제품 backlog가 아니라 관찰 기록, taxonomy, interaction pattern, guide/eval 후보로 자라난다.
- 원자료 provenance가 중요해서 한 프로젝트의 issue log 안에 묻히면 오히려 맥락 복원이 어려워진다.

아직 elendirna 안에 남겨야 하는 것:
- `elf`/MCP tool description, bundle/query/revision_add/sync_record 같은 구체 구현 결정.
- elendirna UX에 직접 들어갈 source-bearing hint, optional frame anchors, scope/provenance guard의 제품 설계.
- N0050 같은 핵심 설계 원칙의 현행 적용처.

분리 후 구조는 3층이 자연스럽다.
1. elendirna vault: 제품 결정과 구현 가까운 원칙만 유지.
2. AI 행동학 vault: raw case, taxonomy, 모델별 행동 관찰, 안내문 실험 기록.
3. github project/repo: eval harness, MCP/tool response prototype, prompt/interface fixture처럼 실행 가능한 실험 코드.

이때 N0064의 transplant/bonsai 관점이 중요하다. 처음부터 모든 revision chain을 복제하기보다, N0075/N0076 같은 raw case는 원본 링크와 함께 두고, 별도 vault에는 bonsai된 요약 entry + source pointer를 심는 편이 낫다. 즉 "독립"은 원자료 절단이 아니라, 원자료를 추적 가능한 상태로 둔 채 새 연구 가지를 키우는 것이다. → see N0064

## N0075/N0076 이슈에 대한 자연스러운 맥락 유도 제안

핵심은 AI에게 "항상 먼저 검색하라"는 규칙을 추가하는 것이 아니다. 그런 규칙은 N0050의 non-compulsive 원칙을 해치고, 실제로는 모델이 체크리스트를 수행했다는 느낌만 만든다. 대신 모델이 claim을 만들기 직전에 관련 entry를 만나기 쉽게 해야 한다. → see N0050

제안 1: source-bearing hint
- `query`, `bundle`, `session_start` 응답에 "이 주제에서 자주 같이 확인되는 source"를 짧게 노출한다.
- 예: "제품 경계/분리 정책 claim 전에는 N0063/N0064를 확인하면 좋음" 같은 한 줄.
- 중요한 점은 명령이 아니라 출처 있는 affordance라는 것. AI가 무시해도 되지만, claim을 만들 때 잡을 손잡이가 생긴다.

제안 2: optional frame anchors
- `query(tag=...)` 결과 옆에 관련 frame/principle entry를 optional anchor로 얹는다.
- 예: `ai-behavior`, `context-guidance`, `project-separation`을 물으면 N0050, N0064, N0075, N0076이 "근거 후보"로 같이 보인다.
- `query(tag=frame)` 같은 의식을 강요하지 않고, 도구 응답이 자연스럽게 옆길을 낸다.

제안 3: scope/provenance guard
- AI가 "표준 init 상태", "core/add-on 경계", "이미 정책이 있다", "이 repo/org의 방향은 X" 같은 범위 claim을 할 때, 답변 표면에 확인 상태를 붙이도록 유도한다.
- 형식은 가볍게: `확인됨: N0063`, `추정: 관련 entry 미확인`, `범위: elendirna core only` 정도.
- 이것도 강제 policy가 아니라, tool description과 응답 예시가 만들어내는 말버릇에 가깝게 둔다.

제안 4: 안내문은 질문형/초대형으로 작성

AI에게 주는 안내는 다음 톤이 좋다.

> 이 주제가 제품 경계, 표준 상태, 기존 결정에 관한 주장으로 이어질 것 같다면, 답변 전에 관련 entry id가 있는지 한 번 찾아보면 좋습니다. 없으면 추정이라고 표시하고, 있으면 `→ see N####`로 붙이세요.

이 문장은 "반드시"가 아니라 "그럴 것 같다면"으로 시작한다. 모델의 자연스러운 판단을 살리면서도, N0075/N0076에서 무너진 바로 그 지점에 retrieval affordance를 둔다.

## 결론

AI 행동학(가칭)은 별도 vault/project로 분리할 가치가 있다. 단, elendirna에서 떨어져 나가는 독립 학문처럼 시작하기보다, N0075/N0076 같은 구체 사례를 source-bearing corpus로 축적하고, 그 위에 taxonomy/eval/tool UX를 얹는 방식이 맞다. 제품 쪽에는 증류된 원칙과 구현 후보만 남기고, 행동 관찰의 raw density는 별도 vault가 감당한다.

[Impact] N0075/N0076의 provenance hint 논의를 별도 AI 행동 관찰 프로젝트 분리 기준으로 확장. 분리 자체는 찬성하되, 큰 명칭이 먼저 행동을 지배하지 않도록 source-bearing corpus와 bonsai/alias 기반 분리를 권고.
