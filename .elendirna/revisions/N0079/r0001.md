## 출발: qdrant 건덕지 탐색
직접 동기는 "서버 모듈에서 sync.jsonl 대체"였으나, jsonl은 append-only 이벤트 로그 — vector store와 카테고리 mismatch (jsonl 대체는 sqlite WAL이나 DuckDB가 맞음).
진짜 fit 지점은 entry note + revision delta에 대한 **semantic recall 보조 레이어**.

## 1차 의문: Obsidian RAG와 같은 모양 아닌가
기술 스택 동일: markdown + 임베딩 + vector DB + 정확매칭 보조.
"왜 Obsidian에서는 미적지근했는데 elendirna에서는 쓸만해 보이는가"를 풀어야 진짜 타당성이 성립.

## 2차 통찰: 청크 문제의 구조적 우회
일반 RAG의 핵심 약점은 **"청크가 의미 단위가 아니다"** — 임의로 자른 문단이 임베딩 공간에서 흐릿한 점을 만듦.
Obsidian이 미적지근한 더 깊은 이유는 사용자가 "뭘 기록할지" 결정 부담을 지다 무너지는 것 (→ see project memory: PKM curation 실패).

elendirna는 schema 차원에서 두 문제를 동시에 우회:
- baseline + revision delta가 기록 단위를 schema로 강제 → "부모 생각에서의 변화량"이라는 의도된 의미 단위.
- 임베딩 단위가 *처음부터* "한 시점의 의미 있는 사고의 이동"으로 발생.
- → vector retrieval의 약점이 데이터 모양에 의해 사전에 해소됨.

[Impact] 즉 이 add-on의 의의는 "RAG를 또 한 번 붙이자"가 아니라 "elendirna의 schema가 RAG 친화적 데이터를 이미 생산하고 있다"는 관찰.

## 차별점 정리 (Obsidian-RAG vs elendirna-semantic-recall)
1. **소비자**: 사람 UI 보조 → agent의 MCP tool. 검색 품질 = agent 추론 품질.
2. **단위**: 임의 청크 → revision delta (의도된 의미 단위).
3. **큐레이션 결정**: 사용자 → schema-as-curation.

## 배치와 경계
- 핵심 elendirna가 아닌 **elen-labs add-on 후보** (→ see project memory: elen-labs 분리).
- **opt-in tool로 격리 필수** — 자동 recall은 N0050 non-compulsive 원칙과 충돌. agent가 명시적으로 호출했을 때만 작동.
- 명시적 `→ see N####` 링크 문화를 흐리지 않도록 semantic recall은 *보조 축*으로만. baseline 그래프(명시적 계보)와 임베딩 공간(암묵적 인접성)이 서로 대체하지 않고 보완.

## 잠정 형태 (묵힘 단계)
- 신규 MCP tool 후보: `semantic_query(text, limit, tag_filter?)` — sqlite hybrid filter + qdrant rank.
- 임베딩 단위: revision body 1개 = 1 vector (entry-level은 너무 거친 듯, 추후 검증 필요).
- 의존성: 임베딩 모델 선택은 별도 결정 (local sentence-transformers vs API).
- 결정은 강요하지 않음 — entry로 simmer.
