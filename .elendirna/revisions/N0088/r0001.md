## Delta

[Change] N0067 v0.5.4 close 직전 화두에서 발산. 해결된 버그 entry를 archived로 두고, 비슷한 버그 재발 시 다시 꺼내는 방안 정리.

## archived 시맨틱 (2026-05-18 검증)

`elf` v0.5.4 기준 archived는 "사라짐"이 아니라 **life cycle 표지**:
- `entry_list()`: archived 포함, `status` 필드로 식별
- `query()` (status 무지정): archived 포함 (검증: N0045 retrieval됨)
- `query(status='archived')`: 명시 필터 작동
- `bundle()`: archived 본문 + revision chain 정상 접근

→ 어느 retrieval 도구로도 archived에 닿음. *기본 작업 시야에서 빠지는* 일은 없음. 따라서 archived 처리해도 *retrieval 기반 재발견*이 작동.

미확인: archived 상태에서 `revision_add` 직접 가능 여부. fallback은 *status를 먼저 draft로 되돌린 뒤 revision_add*.

## 정책: 버그 entry life cycle

### Stage 1 — 발생
- status: `draft`
- 증상·재현·가설 박기

### Stage 2 — 진단
- 코드 검증·외부 모델 cross-validation 누적
- revision chain으로 진단 진화
- status: `draft` 유지 (또는 *해석이 안정화*되면 `stable`)

### Stage 3 — fix 확인
- 라이브 검증 revision 박기 (N0067 r0004 류 마일스톤)
- 잔여 항목 명시 (별 작업 후보로 → see)

### Stage 4 — close
- status: `archived`
- entry는 사라지지 않음. retrieval에 여전히 잡힘.

### Stage 5 — 재발 시 분기 판단

**증상 동일성**으로 분기:
- 같은 메커니즘·같은 증상 → **reopen (D 패턴)**
- 다른 메커니즘이거나 새 증상 → **새 entry + → see archived (A 패턴)**

### Reopen 패턴 (D)

1. `query`/`bundle`로 archived entry 찾기 (기본 retrieval로 닿음)
2. `entry status N#### draft`로 되돌림
3. `revision_add` 한 줄: *"[Change] YYYY-MM-DD 재발 — 새 발현 N####. [Impact] 본 entry close 재검토 필요"*
4. → see 새 발현 케이스 entry (별 트랙)

revision chain이 *"fix → reopen → fix"* 라이프사이클을 그대로 누적함. 별 트래킹 스키마 추가 X.

### 새 entry 패턴 (A 결합)

- 메커니즘 다르면 별 entry로 박고 archived entry를 `→ see` 참조
- baseline에 archived entry 지정 가능 (아이디어 계보 보존)

## 기존 프리미티브로 cover (N0050 비강제 안내 정신)

본 정책은 새 스키마·새 status·새 tag를 추가하지 않음. 기존 `status` 3종 + `revision_add` + `→ see`만으로 reopen 라이프사이클 커버. 별도 *"bug:open/fixed/reopened"* 메타 tag도 도입하지 않음 — revision chain이 같은 정보를 자연 누적.

대안 옵션 정리(채택 X):
- (B) status 변경만 — 흔적 약함 (revision chain에 reopen delta가 없으면 status 변경 사유 안 보임)
- (C) archived 안 함, stable 유지 — entry_list 무거워짐, "여전히 살아있는 버그" vs "fix됐지만 anchor" 구분 안 됨
- (E) 메타 tag 분리 — status와 직교한 추가 axis, cognitive load

## 운용 가이드 (사용자/agent 공통)

- **archived 처리 시점**: fix 확인 + 잔여 항목 명시(별 작업 후보로 → see) **둘 다** 만족할 때. 잔여 있으면 stable 유지.
- **archived 안 하는 경우**: 영구 anchor 가치가 fix 마일스톤보다 클 때(예: 디자인 원칙 entry, 패턴 case-study).
- **재발견 시 검색 키**: 증상 키워드 → `query(title_contains=...)` 또는 tag 검색. archived 포함되므로 기본 query로 충분.
- **reopen 후 close**: 다시 archived로 가는 게 정상. revision chain에 "재발 N회"가 누적되면 N0067 류 systemic 패턴 후보로 격상.

[Impact] 해결된 버그 entry의 라이프사이클이 기존 프리미티브만으로 cover됨. archived가 *retrieval에 살아있다*는 시맨틱이 정책의 핵심 전제. N0050 비강제 안내 정신과 정합 — 별 스키마/태그/도구 추가 X. 향후 버그 entry close 시 본 entry 참조하여 동일 패턴 적용 가능. systemic 재발 패턴(같은 entry가 N회 reopen)은 별 entry로 격상 후보.
