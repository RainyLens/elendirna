## Cons-2 대체안 — `error` level dormant 문제

### 문제 framing 재진단 (사용자 인사이트, 2026-05-20)

> "사실 2는 B로 가면 없어질 내용이긴 한데."

핵심: Elendirna의 error는 JSON-RPC protocol error로 별 channel 처리됨 ([src/error.rs](src/error.rs), [src/mcp/mod.rs:104](src/mcp/mod.rs) `ErrorData::invalid_params`). 응답 본문 `messages[]`에 error level이 거의 안 나타나는 것은 **dormant**가 아니라 **layer 분리**의 자연 결과.

→ Cons-2는 framing 문제. spec 정의로 사라짐.

### 채택안: error level 유지 + spec 정의

**Spec**: 
- 응답 본문 `messages[]`의 `error` level = vault corruption / invariant violation / 응답에 포함되어야 하지만 호출은 성공한 critical state 보고용
- protocol-level JSON-RPC error는 별 channel(`ErrorData::invalid_params` / `internal_error`) 유지
- 두 layer는 직교 — protocol error는 호출 자체 실패, messages[] error는 호출 성공하되 critical state 동봉

### 근거

- syslog RFC 5424 / Rust `log` crate(error/warn/info/debug/trace) / Python `logging`(CRITICAL/ERROR/WARNING/INFO/DEBUG) 모두 error 자리 reserve가 정합
- reserve 비용 없음 (현재 emit 안 해도 spec/enum에는 자리)
- 미래 확장 자연: vault corruption detected, schema invariant violation 등 응답-본문-보고가 자연스러운 케이스 대비

### 대안 (미채택)

- (i) **2-level** (info/warning만) — log idiom의 일부만 가져와 spec 비대칭. 미래 error 케이스 등장 시 spec 재변경
- (ii) **protocol error mirror** — JSON-RPC error 발생 시 응답 본문에도 echo. redundant + protocol error는 응답 본문 없는 케이스 다수

## Cons-3 대체안 — `info` 경계 모호

### 문제

현재 info성 정보가 다수: `next_action`, `hint`, `context_hints`, `handover_status`, `vault_status`, `vault_kind` 등. 모두 messages[]에 통합 시 array 길어지고 info 안에서 또 categorize 욕구 발생.

### 옵션

**(i) info 통합 + sub-category 필드**
```json
"messages": [
  { "level": "info", "category": "guidance",  "kind": "vault_active",    "message": "..." },
  { "level": "info", "category": "status",    "kind": "vault_kind",      "message": "..." },
  { "level": "info", "category": "hint",      "kind": "bundle_policy",   "message": "..." }
]
```
- pros: 모든 메시지 단일 surface. category로 filter 가능
- cons: level + category + kind 3축 — 구조 복잡. category enum 정의 필요

**(iv) info성 필드 보존 + messages는 warning/error만**
```json
"hint": "...",            // 기존 info성 필드 유지
"next_action": "...",     // 동
"context_hints": {...},   // 동
"messages": [             // warning/error만
  { "level": "warning", "kind": "escalated_write", "message": "..." }
]
```
- pros: PR scope 절감. 기존 info 필드의 강한 시맨틱 보존. agent가 messages[] 만 분기하면 됨 (warning/error)
- cons: 통합 spec 미완. info는 다른 모양

**(v) RFC 5424 notice level 추가 — 4-level (info/notice/warning/error)**
```json
"messages": [
  { "level": "notice",  "kind": "vault_active",    "message": "현재 로컬 vault 활성화" },
  { "level": "info",    "kind": "handover_status", "message": "..." },
  { "level": "warning", "kind": "escalated_write", "message": "..." }
]
```
- pros: notice level이 "사용자 알림" 시맨틱과 정확히 일치. RFC 5424 정합
- cons: level enum 4종 — agent 인지 복잡. Rust `log` crate는 5-level인데 notice 없음(error/warn/info/debug/trace)

### 권고

본 PR(B) 진입 시점에 결정 (현재 묵힘 단계). 1차 선호: **(iv) info성 필드 보존**. 근거:
1. PR scope 절감 — info 필드 통합은 N0040 layer 더 깊은 refactor
2. info 시맨틱이 강함 — next_action(action prompt), hint(state-dependent guidance), context_hints(workflow), handover_status(resumption) 모두 명확한 역할. 단일 array에 묻으면 시맨틱 약화
3. agent의 실질 분기 요구는 warning/error에 집중 — info는 narrative reading에 가까움 (level filter 이득 marginal)

2차 후보: **(v) notice level 추가** — info 통합 + notice 카테고리화. (iv)와 (i) 사이 절충. RFC 5424 정합 보너스

(i)는 over-engineering 위험 — level + category 두 축이 같은 정보를 두 번 분류
